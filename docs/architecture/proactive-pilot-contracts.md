# AE v2 local fixture contracts

This prototype validates local fixtures against a subset of the proposed AE v2 design. It does not implement Telar, a production authority, a worker bridge, a route state machine, a broker, persistence, or an external action. The proposed ADR is not ratified by this implementation. The schemas admit only the five Sales → Product → Engineering → Sales event types and the `engineering.scope` and `private_preview.publish` approval payloads. Release, send, CRM, deployment, and other effects have no implementation or accepted event or approval variant here. A valid approval receipt is not permission to execute or publish anything.

## API

`PilotEventSchema` and `PilotApprovalSchema`, with inferred `PilotEvent` and `PilotApproval`, are exported by `src/schema/proactive-pilot.ts`. The strict wire fields follow the supplied AE v2 event, approval, and action-argument contracts, including `rootTaskId`, immutable artifact references and exact arguments. Only lowercase UUIDs, `sha256:` hashes, full lowercase 40- or 64-character commits, real UTC millisecond timestamps, nonnegative safe integer costs and hops up to six are admitted. Executable objects reject unknown fields.

`admitPilotEvent(event: unknown, context: PilotAdmissionContext, prior?: PilotPriorReceipt[]): PilotAdmissionReceipt` validates the schema, supplied current time, tenant, separately supplied actor and authorization reference, optional recipient, and event hash. It returns `status: 'accepted' | 'duplicate'`, the typed event, and the event ID, idempotency key and hash. A prior match requires **all three** fields to match; a collision on either key with any difference throws. The caller must provide complete, trusted, tenant-scoped prior receipts. This is an in-memory comparison, not durable deduplication, atomic admission or exactly-once delivery.

`PilotAdmissionContext` is `{ tenantId, now, expectedRecipientId?, trustedPrincipal, trustedAuthContextRef }`. `trustedPrincipal` has the event actor shape. The caller must derive these inputs from an authenticated server boundary, not copy them from an event or model output. The function does not verify identity, membership, ACL, route order, root/parent causality, root budget, grants, evidence provenance, or approval state. Those checks require an authority outside this prototype. In particular, a matching actor in an envelope is not itself evidence of authority.

`validateScopeApproval(payload: unknown, context: PilotApprovalContext): PilotApprovalReceipt` accepts either scope or private-preview payload and returns `{ status: 'valid', payloadHash, approval }` or throws. Context is `{ tenantId, now, expectedPayloadHash, currentPayload, currentPolicyVersion, trustedHuman: { principalId, active, roles }, latestDecision: { payloadHash, principalId, decision }, grantActive, reservationActive, killSwitch }`. The caller must derive the current human, latest decision, policy, grant, reservation and current payload from trusted, fresh server-side sources. The guard requires the decision to be approved by that active human with the required role, bound to the expected payload hash, and requires the exact current payload and arguments hashes, current policy, active grant/reservation, disabled kill switch and unexpired scope. It cross-checks repository, commit, required referenced artifacts and relevant reservation/cost or build digest. A changed spec, candidate, audience, target or other field changes the payload hash and needs a new approval. This is a local fixture guard, not proof of single-use consumption or a substitute for a broker's atomic, immediately-before-dispatch checks.

`PilotError.code` and its message are stable error identifiers: `PILOT_INVALID_JSON`, `PILOT_INVALID_EVENT`, `PILOT_INVALID_APPROVAL`, `PILOT_TENANT_MISMATCH`, `PILOT_PRINCIPAL_MISMATCH`, `PILOT_RECIPIENT_MISMATCH`, `PILOT_EVENT_EXPIRED`, `PILOT_HASH_MISMATCH`, `PILOT_DUPLICATE_CONFLICT`, `PILOT_APPROVAL_EXPIRED`, `PILOT_APPROVAL_BINDING_MISMATCH`, and `PILOT_APPROVAL_DENIED`.

## JSON boundary and hashes

For raw JSON, call `parsePilotJson(text)` **before** either validator. It rejects duplicate keys, including escaped-equivalent keys, malformed JSON, unsafe integers, fractional or exponent number tokens, unsupported values, invalid Unicode and documents over one million UTF-16 code units. Passing an already parsed object loses evidence of duplicate input keys; neither Zod nor these guards can reconstruct it. The guards accept objects for local fixture use, so an integrator must enforce the raw parsing boundary itself.

`canonicalJson`/`canonicalHash` cover a restricted JSON domain: null, booleans, well-formed Unicode strings, safe integer numbers, arrays and plain data objects, with a depth limit of 64. They reject floats, unsafe integers, nonfinite numbers, lone surrogates, cycles, accessors, symbols and unsupported objects; keys sort by UTF-16 code units and strings and integers use ECMAScript JSON serialization. The event hash omits `canonicalHash`; an approval hash covers the whole approval and its argument hash covers the exact `arguments` object. This is a bounded JCS-compatible subset with local test vectors, **not a claim of full RFC 8785 conformance**. Qualification against a vetted implementation and the full required vector set is needed before any integration that depends on interoperation.

No API call or model judgment is used. All contract, hash and authorization comparisons are deterministic; text in fixtures is data and has no authority. No credentials, paid calls, external effects, network execution or product state are involved.
